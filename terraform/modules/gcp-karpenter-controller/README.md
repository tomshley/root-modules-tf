# GCP Karpenter Controller

This pre-1.0 module installs the exact `cloudpilot-ai/karpenter-provider-gcp` `0.6.0` CRD and controller charts. It composes `gcp-karpenter-crds` and `gcp-karpenter-controller-release`; a consumer that needs the controller without the CRDs, or the CRDs without the controller, composes those two directly. Apply `gcp-karpenter-prereqs` first. That module creates the controller Google service account and delegates every Workload Identity and project IAM principal grant to `gcp-gke-workload-identity`; this module only annotates the Helm-managed Kubernetes ServiceAccount with its resulting Google service-account email.

The controller image tag is pinned to `v0.6.0` and its repository to the upstream `public.ecr.aws/cloudpilotai/gcp/karpenter`; `use_patched_dual_stack_image` or `controller_image` replaces both when a different build is required — see *Dual-stack clusters* below. The v0.6.0 chart exposes repository, tag, and pull-policy values but no image-digest value, so an image digest cannot be pinned through its supported chart interface.

## Dual-stack clusters

Provider `0.6.x` creates every node's primary NIC IPv4-only — it never sets `NetworkInterface.stackType`. On a dual-stack (`IPV4_IPV6`) cluster, GKE's control-plane IPAM assigns IPv4 and IPv6 pod CIDRs together, so a node whose NIC carries no IPv6 address receives neither: `spec.podCIDRs` stays empty, `netd` fails at startup, the CNI plugin never initializes, and the node sits `NotReady` until Karpenter reaps it. Clusters built by this repository's `gcp-gke-cluster` module are always dual-stack, so with the upstream image a Karpenter node can never reach Ready on one.

`use_patched_dual_stack_image = true` is the whole fix: the module resolves a vendored build of the same provider release — published at `registry.gitlab.com/tomshley/brands/global/tware/tech/products/provisioning/vendored/karpenter-provider-gcp/karpenter`, tagged `v<chart>-dualstack` — that sets `stackType` from the cluster's IP allocation policy. Where the registry is private, a `read_registry` deploy token rendered into the controller namespace and named in `image_pull_secrets` carries the pull; mirroring the image into a cloud-local registry the node service account already reads avoids the pull secret entirely. `controller_image` remains the escape hatch for an arbitrary build and is mutually exclusive with the flag. The `gcp-gke-karpenter-controller-image` example shows the wiring.

Karpenter applies the generic `gke-<cluster>-node` tag and, since provider v0.4.0, the cluster-id-bearing `gke-<cluster>-<cluster-id[:8]>-node` tag that GKE's auto-created firewall rules actually target — earlier provider versions emitted only the generic tag, which matched no auto-created rule and left nodes unreachable from the control plane. `GCENodeClass.spec.networkTags` is appended after both derived tags, never replacing them, so an overlay tag cannot strip the firewall coverage. Pass `node_network_tags` through to every NodeClass unchanged.

## Cluster location contract

The controller takes two location settings with different meanings. `cluster_location` feeds instance-type discovery and accepts a region or a zone — the controller derives the compute region from it. `node_location` is the exact location used to address the cluster in the provider's GKE node-pool API paths, for both the existence check and pool creation; when unset, the controller defaults it to `cluster_location`. The default is correct for a regional cluster (whose location is its region) and for a zonal cluster whose `cluster_location` is already its zone, so `node_location` should normally be omitted — set it only when `cluster_location` is a region but the cluster itself is zonal. A zone against a regional cluster makes every node-pool existence check and creation miss with 404 and the controller retries indefinitely while NodeClasses still admit cleanly.

The controller no longer creates its own template node pools (removed in provider v0.4.0). It bootstraps nodes from the instance template of an existing RUNNING pool, discovered as `default-pool`, else the first RUNNING pool in alphabetical order, else a `karpenter-fallback` pool it creates. Alphabetical discovery is incidental, not a contract — a cluster whose pools sort so that an unrepresentative pool comes first silently bootstraps from it. Set `bootstrap_node_pool_name` to pin the source pool deterministically; leaving it null keeps upstream discovery and emits no Helm value. If upgrading an install that predates the discovery behavior, the legacy `karpenter-default`/`karpenter-ubuntu`/`karpenter-cos-arm64`/`karpenter-ubuntu-arm64` pools are no longer used by the provider and can be deleted.
